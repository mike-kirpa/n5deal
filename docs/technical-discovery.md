# Technical Discovery — N5Deal Virtual Data Room

## 1. Executive Summary

Discovery date: 2026-10-15. Application snapshot: `virtual-data-room`, commit `4a787b43bd921be48f5ab11e30828b97b8c5ee0c`; the application worktree was clean at the initial check. This is a static implementation review, not an executed QA assessment or a release recommendation. Source references below are relative to `virtual-data-room/`, except references explicitly prefixed `n5deal-qa-assignment/`. Line numbers refer to this snapshot.

Evidence labels used throughout:

- **Fact:** directly observable code or documentation content; runtime success is not implied.
- **Documented limitation:** explicitly described MVP omission, not automatically a defect.
- **Hypothesis:** a possible failure requiring the stated verification; severity describes its impact if reproduced.
- **Unknown:** cannot be established without an approved test environment or product clarification.

The implementation contains a React SPA, a NestJS REST API, Prisma/PostgreSQL metadata and Supabase Storage signed operations. All seven REST controllers, comprising 33 routes, are inventoried in section 4. The core requested folder, PDF and read-only sharing workflows have implementation paths. Access decisions use the actual resource's room and ancestor chain, with owner-only mutations and shared reads; no confirmed IDOR is established by this review. Sources: `apps/api/src/app.module.ts:13-26`; controllers in section 4; `apps/api/src/common/access/resource-scope.ts:17-67`; `apps/api/src/common/access/resolve-access.ts:17-96`.

The first verification priorities are:

1. **Recipient identity and access boundaries:** registration issues a token without an email-ownership verification step, while USER shares match the account's email. Endpoint-level isolation also needs verification beyond helper mocks. Sources: `apps/api/src/auth/auth.service.ts:24-57`; `apps/api/src/common/access/resolve-access.ts:35-55`; hypotheses H01–H02.
2. **Concurrent naming and share creation:** conflict checks and share deduplication precede separate writes; the schema does not enforce sibling-name uniqueness or one active grant per target/mode/recipient. Sources: `apps/api/src/common/resolve-name.ts:19-44`; `apps/api/src/folders/folders.service.ts:68-85,271-290`; `apps/api/src/shares/shares.service.ts:37-65`; `apps/api/prisma/schema.prisma:32-92`; H03–H04.
3. **Upload and storage consistency:** completion trusts object existence/size, browser retries repeat PUT before completion, and database deletion precedes best-effort storage cleanup. Sources: `apps/api/src/files/files.service.ts:99-125,189-203`; `apps/api/src/storage/storage.service.ts:77-90`; `apps/web/src/features/data-room/upload/use-upload-queue.ts:46-75,132-138`; H05–H07.

Five backend unit-test files contain 42 declared cases using mocked database operations; one Supertest case checks `/health`. No frontend or browser tests were found. These tests were read, not executed; coverage percentages and pass/fail status are unknown. See section 8 for precise scope.

README claims require care: it describes an existing `Share.role`, although the current Prisma schema omits it and the initial migration creates it; it also describes allow-all CORS when unset, although bootstrap requires a nonempty `CORS_ORIGIN`. These are confirmed documentation/schema discrepancies, not proof of a deployed failure. Sources: `README.md:60,149,163`; `apps/api/prisma/schema.prisma:79-92`; `apps/api/prisma/migrations/20260815081856_init/migration.sql:7-8,57-69`; `apps/api/src/main.ts:9-18`.

No services, migrations, dependency installation, tests or deployed-application requests were run. No real `.env` files were read. The only authored artifact for this discovery is this report; the existing QA plan and framework remain the baseline for later work.

Main flows, grounded in their call sites:

1. **Identity:** login/register → DTO validation → normalized email + bcrypt → signed JWT → localStorage → bearer interceptor → global guard verifies signature/expiry and sets `request.user` → controller reads `CurrentUser`. Registration creates user and default room together. Sources: `apps/api/src/auth/auth.service.ts:24-90`; `apps/api/src/auth/auth.module.ts:11-21`; `apps/api/src/common/guards/jwt-auth.guard.ts:29-60`; `apps/api/src/common/decorators/current-user.decorator.ts:13-18`; `apps/web/src/features/auth/auth-provider.tsx:35-49`; `apps/web/src/lib/api.ts:3-26`.
2. **Metadata read:** controller parses IDs/query → service loads target and constructs scope → `requireAccess` → Prisma query/select → response → TanStack Query cache → explorer/viewer. Folder/file scope includes the room and current ancestor folders; file scope uses the file's current `folderId`. Sources: `apps/api/src/common/access/resource-scope.ts:34-107`; `apps/api/src/common/access/resolve-access.ts:85-96`; `apps/api/src/folders/folders.service.ts:88-168`; `apps/api/src/files/files.service.ts:227-260`; `apps/web/src/features/data-room/hooks.ts:57-74`.
3. **Sharing:** owner resolves the target → reuse/create active share → recipient uses matching account email or public token → reads are authorized against the requested resource's chain. Revocation timestamps one share; other covering grants can still authorize access. Sources: `apps/api/src/shares/shares.service.ts:37-65,119-135,212-259`; `apps/api/src/common/access/resolve-access.ts:43-75`.
4. **File bytes:** authorized intent → pending DB row + signed upload URL → browser multipart PUT to storage → completion checks object info → DB marks uploaded → later authorized URL issuance → browser reads storage directly. Sources: `apps/api/src/files/files.service.ts:49-125,206-260`; `apps/web/src/features/data-room/upload/api.ts:15-64`; `apps/api/src/storage/storage.service.ts:21-53,77-90`.

The folder hierarchy stores both adjacency (`parentId`) and a materialized UUID path (`ancestor/self/`); the room ID is separate. Creation appends a UUID to the parent path. Rename preserves paths; file moves change `folderId` and therefore inherited access on subsequent requests. Sources: `apps/api/prisma/schema.prisma:32-65`; `apps/api/src/folders/folders.service.ts:56-85,189-192`; `apps/api/src/files/files.service.ts:153-185`; `apps/api/src/common/access/resource-scope.ts:49-67`.

Listing indexes exist for room ownership, folder/file sibling ordering and share keysets (`apps/api/prisma/schema.prisma:29,45-47,64-65,90-91`). This supports the design described in `README.md:157-163`; no database query plan or 100,000-file measurement was obtained. Subtree deletion intentionally loads all matching folder IDs and storage keys, unlike paginated user listings (`apps/api/src/folders/folders.service.ts:247-268`).

## 4. REST API Inventory

**Static contract conventions:** JWT means `Authorization: Bearer <accessToken>` through the global guard; a public token is a path token, not a JWT. Owner implies read permission. Anonymous protected calls should return 401; insufficient resource access throws 404, not 403. Path resource IDs use `ParseUUIDPipe`; DTOs validate body/query UUIDs and enum values. Invalid input/cursors should return 400. Unknown body properties are stripped by the validation whitelist. Sources: `apps/api/src/common/guards/jwt-auth.guard.ts:29-60`; `apps/api/src/common/access/resolve-access.ts:85-96`; `apps/api/src/main.ts:19`; controllers/DTOs below; `apps/api/src/common/parse-cursor.ts:8-19`.

Success codes are derived from controller decorators and Nest's normal defaults, not observed HTTP responses: GET/PATCH 200; POST 201 unless overridden; login explicitly 200; DELETE explicitly 204. Responses serialize service return values; there is no global response envelope in `apps/api/src/main.ts`. All 33 routes below are suitable for future black-box API checks, with storage-dependent routes requiring a dedicated configured bucket.

`Page<T>` means `{items:T[], nextCursor:string|null}`. Shared pagination query **P** is `cursor?` (opaque string) and `limit?` (integer 1–100, default 50): `apps/api/src/common/dto/pagination-query.dto.ts:5-15`; `apps/api/src/common/pagination.ts:1-19`. Follow `nextCursor` until null, even if a page is empty.

## 5. Authentication and Authorization Model

### Identity resolution

JWT signing uses `{sub:userId,email}` and a seven-day expiry (`apps/api/src/auth/auth.service.ts:89-90`; `apps/api/src/auth/auth.module.ts:11-16`). The global guard exempts routes with public metadata, otherwise extracts a case-sensitive `Bearer` header, verifies the token, and assigns `user.id=payload.sub` and `user.email=payload.email` (`apps/api/src/common/guards/jwt-auth.guard.ts:29-60`). `CurrentUser` returns that request identity (`apps/api/src/common/decorators/current-user.decorator.ts:13-18`).

The guard does not query the user table. `/auth/me` checks user existence; non-owner share decisions independently look up the current database email rather than trusting the JWT email claim (`apps/api/src/auth/auth.service.ts:78-86`; `apps/api/src/common/access/resolve-access.ts:23-55`). No email-verification state exists in `User`, and registration immediately returns a token; this supports H01, not a claim that an existing user's password can be bypassed (`apps/api/prisma/schema.prisma:11-18`; `apps/api/src/auth/auth.service.ts:24-57`).

### Inheritance, boundaries and revocation

For a file nested under A/B, the chain is `[DATAROOM, A, B, FILE]`; a matching share at any one entry grants VIEWER. A folder grant does not cover its parent, siblings or the room itself. Types are part of the match, not just IDs. Authenticated ownership takes precedence. Sources: `apps/api/src/common/access/resource-scope.ts:17-67`; `apps/api/src/common/access/resolve-access.ts:23-75`.

Owner-only calls cannot be made writable by acquiring a public or email share: `AccessLevel` is only `OWNER|VIEWER|NONE`, and `requireAccess` compares ranks before returning (`apps/api/src/common/access/access.types.ts:3,18-29`; `apps/api/src/common/access/resolve-access.ts:85-96`). The current model has no operational editor role, regardless of the older README/migration description.

Authenticated breadcrumbs resolve the topmost active matching USER grant, omit unauthorized ancestor names and return a null room name below a folder-share boundary (`apps/api/src/common/access/resolve-access.ts:108-138`; `apps/api/src/folders/folders.service.ts:109-168`). File metadata still contains actual `folderId`/`dataRoomId`, and folder-content items contain parent IDs (`apps/api/src/files/files.service.ts:238-245`; `apps/api/src/common/contents.ts:73-91`). Whether these opaque identifiers must also be hidden is an open product question; names above the boundary are deliberately protected.

Revocation updates **one** share's timestamp, not an access-deny rule overriding all grants. Active queries exclude that row; overlapping room/folder/file grants can continue to authorize access. Recreating a revoked public grant creates a new random token; the old revoked token remains 410. File moves immediately change the ancestor chain used by later requests, while a direct FILE grant remains attached to its unchanged file ID. Sources: `apps/api/src/shares/shares.service.ts:40-65,119-135`; `apps/api/src/common/access/resolve-access.ts:43-75,149-159`; `apps/api/src/common/access/resource-scope.ts:49-67`; `apps/api/src/files/files.service.ts:153-185`.

Revocation blocks later API URL issuance once observed by the access query; it does not cancel an already-issued storage URL or erase already-downloaded bytes. View/download URLs request a 300-second TTL; actual provider enforcement and browser caching need verification (`apps/api/src/storage/storage.service.ts:5,31-53`). An in-flight request may also have passed its check before revocation. These boundaries must inform the expected result instead of assuming immediate byte-level revocation.

## 6. Folder and File Lifecycle

### Folder operations and listings

Creation checks room ownership, validates parent membership and checks sibling folder names, then writes a UUID ID/path and normalized `nameLower`. Rename checks siblings excluding itself, updates the name, and preserves hierarchy. Folder conflicts return 409; files and folders have separate name namespaces. Sources: `apps/api/src/folders/folders.service.ts:46-85,171-193,271-290`; `apps/api/src/common/name-lower.ts:7-8`; `apps/api/src/common/resolve-name.ts:30-35`.

`fetchContents` lists one level, folders before files, then `(nameLower,id)` ascending within each type. The cursor tags folder versus file so a page can cross that boundary; only completed files are listed. Exactly a full page of final folders may return a cursor leading to an empty final page if no files exist; clients must terminate on null cursor, not assume every next page is nonempty. Sources: `apps/api/src/common/contents.ts:107-193`; cursor shape/decoders: `apps/api/src/common/pagination.ts:9-93`. Invalid cursor decoding is converted to 400 (`apps/api/src/common/parse-cursor.ts:8-19`). Cursors do not represent a frozen snapshot; rename/move during pagination can change ordering, so specify whether concurrent-edit listing stability is required.

Deletion preview counts descendants excluding the selected folder, completed files across that subtree and their stored sizes. Actual deletion also removes pending file rows. DB file/folder removals occur in one transaction; storage deletion follows the commit in chunks of 100, and cleanup errors are suppressed. Shares referencing deleted resources are not removed. Sources: `apps/api/src/folders/folders.service.ts:196-268`; `apps/api/src/storage/storage.service.ts:5-6,60-70`; `apps/api/prisma/schema.prisma:79-92`. Received-share listing filters absent targets; public reads return not found (`apps/api/src/shares/shares.service.ts:186-208,268-317`; `apps/api/src/public/public-shares.service.ts:189-215`).

Verify whether sharing pending files should be disallowed; ordinary UI listings do not expose them.

### Rename, move, view, download and deletion

File upload/rename/move use `resolveName`, which appends ` (1)`, ` (2)` before the last-dot extension, checks case-insensitive sibling files and excludes self when renaming/moving. It does not check folder names, truncate suffixed output to the input length limit, or lock the name check and write together (`apps/api/src/common/resolve-name.ts:4-44`; `apps/api/src/files/files.service.ts:71-92,139-149,175-185`). Parallel naming is H04; length-at-conflict is an additional boundary case for the same tests.

Moves are within the same data room, including root via null or omitted `targetFolderId`; file bytes and `storageKey` are unchanged (`apps/api/src/files/files.service.ts:153-185`). Read metadata and view/download URLs require a completed upload and VIEWER scope. Download signing supplies the current filename; view signing omits the download option (`apps/api/src/files/files.service.ts:206-260`; `apps/api/src/storage/storage.service.ts:31-53`). Actual PDF rendering, response headers and filename handling are environment/browser checks.

Single-file deletion removes the DB row first and ignores object-removal failures (`apps/api/src/files/files.service.ts:189-203`). Folder deletion has the analogous transaction-then-cleanup boundary. Already-issued URLs may continue to read an orphan object until expiry if cleanup fails; an in-flight upload may recreate/write an object after metadata deletion. Verification needs controlled failure injection or bucket observability (H07). This is separate from abandoned-upload GC, explicitly omitted in `README.md:95`.

### Cache, permissions and error handling

Query keys include room identity for root contents and folder pickers; public data includes token plus folder/file identity. User identity is not in most keys, so login/logout deliberately clears all queries. Sources: `apps/web/src/features/data-room/hooks.ts:19-36`; `apps/web/src/features/sharing/components/public-contents-browser.tsx:37-45`; `apps/web/src/features/sharing/public-file-view-page.tsx:24-34`; `apps/web/src/features/auth/auth-provider.tsx:33-49`. These controls deserve regression checks; README's historical cache-bug account (`README.md:183`) is not evidence the old bug remains.

The shared Axios client adds a bearer token to every request when present. On a non-login/register 401 it clears localStorage and usually hard-redirects to login; public `/share/` pages suppress that redirect so an expired login does not interrupt anonymous link viewing. `AuthProvider.hasToken` is local component state, initialized once; there is no cross-tab storage listener in this provider. Sources: `apps/web/src/lib/api.ts:21-50`; `apps/web/src/features/auth/auth-provider.tsx:14-21,35-49`. Verify same-tab account changes, browser back, cross-tab logout and expired-token public browsing; local logout is not server-side JWT revocation.

Owner checks hide upload/create/share and mutation menus; viewers retain file download. These are UI conveniences, while backend OWNER requirements remain the security boundary. Sources: `apps/web/src/features/data-room/components/folder-explorer.tsx:30,88-138`; `apps/web/src/features/data-room/components/contents-table.tsx:42-45,230-242`; `apps/web/src/features/data-room/components/file-row-menu.tsx:40-63`; service checks in section 5.

Lists use infinite queries, sentinel loading and explicit Load more/Retry fallbacks. Initial errors are shown when no cached data exists; a later error can leave existing cached rows visible. Default queries retry once and do not refetch on window focus; no polling interval is configured in the reviewed content/share hooks. Revoking a grant in one session does not push cache invalidation to the recipient. Sources: `apps/web/src/main.tsx:9-15`; `apps/web/src/features/data-room/hooks.ts:57-95`; `apps/web/src/features/data-room/components/contents-table.tsx:63-92,141-165`; `apps/web/src/features/sharing/hooks.ts:62-85`; H08.

## 10. Recommended Automation Candidates

### Minimal approach for the separate QA repository

Retain Playwright + TypeScript in `n5deal-qa-assignment`; its initial config/package already exist and were only inspected. Later, use separate API and browser projects/base URLs, with APIRequestContext for HTTP checks and Chromium for a small browser suite. Keep environment-specific URLs/QA credentials outside committed source; the application uses distinct API and web origins (`apps/web/src/lib/api.ts:17-19`; `README.md:19-21`). Do not add app-source imports, Prisma access or service-role credentials to ordinary black-box tests.

Use separate authenticated contexts for owner A, recipient V and unrelated user B, plus a token-only context with no Authorization header. Generate unique run/worker names and UUID-scoped fixtures; isolate each test under an owned QA folder. Prefer serial execution until data isolation is established, then use isolated parallel tests; only dedicated race scenarios should share targets intentionally. Obtain JWTs through public auth routes; API setup is compatible with the implemented contracts in section 4. Do not create a new room or account for every test because no deletion endpoint exists.

Cleanup should revoke every created share while its resource still exists, then delete the test subtree/file as its owner. Track IDs from setup, including incomplete intents, and collect failure evidence before cleanup. Deleting resources first makes share revocation fail ownership resolution; dangling share records have no black-box removal endpoint (`apps/api/src/shares/shares.service.ts:119-135,212-219`). Accounts/rooms and orphaned storage need an environment reset or operator-owned cleanup mechanism. Keep signed URLs/tokens/passwords out of published traces/reports; browser traces and storage-state files may contain them.

Testing boundaries:

| Layer | Appropriate assertions | What it cannot establish |
|---|---|---|
| Black-box API | Status/payload validation, ownership/Viewer denial, inheritance, token scoping, fresh-request revocation, pagination, naming, move, deletion, upload intent/PUT/complete using supported storage contract. | DB rollback, orphan-object absence, production bucket policy or guaranteed concurrency scheduling. Use a client-authorized bucket upload key only, never the service-role key. |
| Browser E2E | Real login, cache isolation, owner/Viewer actions, drag/drop/progress/retry, PDF embed/fallback, download events/name, share copy/navigation, refresh and keyboard actions. | UI request interception proves handling of simulated responses, not a real backend/storage rollback. Native PDF rendering may need headed/manual confirmation alongside HTTP byte checks. |
| Internal integration / fault injection | DB/bucket inspection, transaction races, storage removal/signing/info failures, abandoned-row cleanup and schema/migration alignment. | Requires separate test-only infrastructure, controlled dependencies or operator observability. It cannot be claimed as completed by an external Playwright status-code test. |
